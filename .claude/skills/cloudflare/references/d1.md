# D1: schema, data, backups

D1 is SQLite at the edge. Use SQLite types and syntax: `INTEGER PRIMARY KEY`, `TEXT`, `REAL`, ISO-8601 `TEXT` timestamps, and `CHECK` constraints for enums such as role and size. Foreign keys are enforced. Keep migrations small and additive.

## Migrations

```bash
cf d1 migrations create DB add_microchip_to_pets     # writes api/migrations/NNNN_add_microchip_to_pets.sql
cf d1 migrations list   DB --env staging --remote    # what's pending
cf d1 migrations apply  DB --local                   # 1. local
cf d1 migrations apply  DB --env staging --remote    # 2. staging (free)
CF_APPROVED=1 cf d1 migrations apply DB --remote     # 3. production (ask first, after a backup)
```

`DB` is the binding name, so the same command works in both environments; `--env` picks the database.

Rules, and why they matter:
- **Never edit an applied migration.** D1 records applied filenames, so an edited file silently never runs elsewhere. Write a new migration instead.
- **Prefer additive changes**, such as new tables and nullable columns. The deployed Worker keeps running during a migration, and old code must survive the new schema.
- **Order: migrate, then deploy code that uses the new schema.** To remove something, deploy code that stops using it first, then migrate.
- SQLite `ALTER TABLE` is limited. Renaming or retyping a column means create the new table, copy, drop, and rename, all in one migration. Show the owner that plan before production.

## Before any production migration: backup

```bash
mkdir -p backups
cf d1 export DB --remote --output backups/patiamor-db-$(date +%Y%m%d-%H%M).sql   # read-only, allowed
cf d1 time-travel info DB                                                        # note the current bookmark
```

Tell the owner the backup file and the Time Travel bookmark when asking for approval. Those are the undo path.

## Querying

```bash
cf d1 execute DB --local --command "SELECT * FROM pets LIMIT 5"
cf d1 execute DB --env staging --remote --command "SELECT count(*) FROM pets"
cf d1 execute DB --remote --command "SELECT count(*) FROM pets WHERE adopted_at IS NULL"   # prod read: allowed
```

Writes to production data (`INSERT`/`UPDATE`/`DELETE`, or `--file`) need approval, including "quick fixes". `DELETE`/`DROP`/`TRUNCATE` need approval on staging too.

**Production data is real people's data**: adopters' contact details and shelters' records. Query only what the task needs. Don't paste personal data into chat beyond counts and IDs, and never copy production rows into staging or local seeds.

## From the Worker (TypeScript)

```ts
const { results } = await c.env.DB
  .prepare('SELECT id, name FROM pets WHERE shelter_id = ? AND adopted_at IS NULL LIMIT ?')
  .bind(shelterId, 50)
  .all<{ id: string; name: string }>();

await c.env.DB.batch([            // atomic: all statements commit or none do
  c.env.DB.prepare('UPDATE pets SET adopted_at = ? WHERE id = ?').bind(now, petId),
  c.env.DB.prepare('INSERT INTO audit_log (actor_id, action, pet_id) VALUES (?, ?, ?)').bind(userId, 'adopted', petId),
]);
```

Always use `?` placeholders with `.bind()`; never interpolate user input into SQL. Role checks (admin, shelter, adopter) belong in the Worker before the query runs, and a shelter's queries must always be scoped by its `shelter_id`.

## Locations and distance

Listings never store addresses. Every pet, litter and shelter points to a `places` row (a barrio/sector centroid picked from a list), which is a privacy rule as much as a data model. D1 can't load SpatiaLite, and doesn't need to: SQLite math functions are enabled. Filter with an indexed bounding box, then compute the exact distance:

```sql
-- ?1 lat, ?2 lng, ?3 radius km, ?4 = km/111, ?5 = km/(111*cos(radians(lat)))
SELECT d.*, 6371 * acos(min(1, cos(radians(?1)) * cos(radians(p.lat)) * cos(radians(p.lng) - radians(?2))
                             + sin(radians(?1)) * sin(radians(p.lat)))) AS km
FROM pets d JOIN places p ON p.id = d.place_id
WHERE d.status = 'available'
  AND p.lat BETWEEN ?1 - ?4 AND ?1 + ?4 AND p.lng BETWEEN ?2 - ?5 AND ?2 + ?5
  AND km <= ?3
ORDER BY km;
```

The adopter's position comes from one of three sources:
- their chosen place;
- `request.cf.latitude`/`longitude` (IP-based, city-level, no permission prompt);
- browser geolocation rounded to 2 decimals (about 1 km) before it reaches the API.

Don't store precise adopter coordinates.

`places` comes from GeoNames' `DO.txt` (CC BY 4.0; the app credits "GeoNames" in the place picker).
- `api/scripts/build_places.py` generates two files: `migrations/0003_places.sql` (about 12,900 rows) and `src/places/data.json`, a compact copy bundled into the Worker.
- Place autocomplete (`/api/places`), nearest-place lookup (`/api/places/nearest`) and `/api/whereami` all run in Worker memory from that JSON, so they cost **no D1 reads**. D1's `places` table exists for foreign keys and the distance SQL.
- The script handles duplicate names (via section hints), messy province names ("Provincia de…") and everyday aliases ("naco", "los mina").
- Loading the full table costs about 52,000 row writes (roughly half the free daily quota). Never re-apply it to two environments on the same day.
- To change places, edit the script and regenerate into a **new** migration (`0004_…` with `INSERT OR IGNORE` / `UPDATE`). `0003` must never change once applied.

## Disaster recovery (ask first)

- Code broke but data is fine: `cf rollback <version-id>`.
- Bad migration or bad write: prefer a forward-fix migration. As a last resort, `CF_APPROVED=1 cf d1 time-travel restore DB --bookmark <bookmark>` rewinds the whole database, losing every write since. Spell that loss out to the owner.
